# Analyze OpenCanbox E2E Logs

You have been asked to analyze an E2E log file (`dump_*.log`) generated by the `canbox_e2e_logger.py` script to identify bugs or anomalies in protocol translation.

## Analysis Workflow

When the user provides a log file and a scenario description, follow these steps strictly:

### 1. Read and Contextualize the Log
* Read the provided `dump_*.log` file.
* Identify the primary streams:
  * `[CAN]`: Raw CAN frames from the vehicle bench (ID, DLC, DATA).
  * `[APP_UART_RX]` / `[APP_UART_TX]`: Hexadecimal serial bytes exchanged between the OpenCanbox Core app and the Head Unit.
  * `[ORIG_CANBOX]`: (Optional) Reference serial bytes from the original OEM Canbox.

### 2. Decode the Traffic
* **Identify CAN intent**: Trace the codebase (e.g., `src/profiles/`) to decode what the `[CAN]` frames represent in the user's described scenario (e.g., Steering wheel button press, Door status).
* **Identify Head Unit intent**: Decode the `[APP_UART_TX]` packets by referencing the C driver implementations (e.g., `src/protocols/hiworld_protocol.c`). Check if the checksums, opcodes, and data lengths match the protocol standard.

### 3. Pinpoint the Translation Bug
* Compare the decoded CAN state to the Head Unit output.
* If `[ORIG_CANBOX]` logs are present, compare `[APP_UART_TX]` against `[ORIG_CANBOX] RX` to see exactly where OpenCanbox's output diverges from the OEM reference unit.
* Identify whether the bug originates in:
  1. Failing to parse the CAN frame correctly (Core Profile layer).
  2. Failing to pack the serial packet correctly (Protocol layer).
  3. A miscalculation of the protocol checksum, length, or framing bytes.

### 4. Propose the Resolution
* Present your findings to the user. Use a Markdown Artifact report if the analysis is extensive.
* Provide a clear timeline of the failure mapping the log timestamps.
* Provide the proposed C code fix. **CRITICAL:** The proposed fix must strictly adhere to the boundaries defined in `AGENTS.md` (Pure C99, no heap allocation, no blocking code).
